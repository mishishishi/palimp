## What 1.10.0 actually changes

Four new runtime files, four changed ones and five version bumps.

| file | change |
| --- | --- |
| `libs/core/src/PalimpDrawerAction.ts` | **new types** `PalimpDrawerAction` `{ id, label, confirm?, needsPublishToken?, run(user) }` and `PalimpDrawerActionResult` `{ message, href? }` |
| `libs/core/src/PalimpDrawerActionsContext.ts` | **new value export** `PalimpDrawerActionsContext`, `createContext<ReadonlyArray<PalimpDrawerAction>>([])`. Imports only `createContext` |
| `libs/core/src/index.ts` | re-exports both from `@palimp/core` |
| `libs/core/src/Admin/Devtools/useDrawerAction.ts`, `DrawerActionButton.tsx` | **new**, admin-only: one `useMutation` per action, the confirm, the states and the result line |
| `libs/core/src/Admin/Devtools/DevtoolsContent.tsx` | renders one `DrawerActionButton` per action, between Publish and the divider |
| `libs/core/src/Admin/Devtools/PublishStatusModal.tsx` | `dispatchCause(error, button = "Publish")` is exported and names the retry button. **Publish's own text is byte-identical** |
| `libs/publish-github/src/react.tsx` | **new prop** `extraTargets?: ReadonlyArray<GithubExtraTarget>` on `PalimpGithubPublishProvider`, mapped into drawer actions and concatenated with any parent value. `GithubExtraTarget` is exported from `./react` |

**No adapter contract, store, schema or `exports` map moved. No peer range changed.** With no
`extraTargets` the drawer renders exactly as at 1.9.0 — so the version bump alone is safe, and
the feature is one prop on top.

### What the editor sees

1. **A `Publish live site` button under Publish**, full width, the drawer's own antd look.
2. **A confirm before anything happens**, with **Cancel focused** — Enter is the harmless choice.
   Title, body and OK text are this host's strings.
3. **`Running...`** (disabled) for the dispatch plus the run lookup, ~4 s observed.
4. **Then a persistent line under the button**: `Run <id> started`, linked to the run on GitHub
   (new tab) — or, on failure, `Publish live site failed` with the button still enabled as the
   retry, the error message, and the same plain-language cause the status modal uses
   (auth vs. everything else). It stays until the next press. **No polling** — the line says the
   run started, not that it finished; the link is how to follow it.

### Behaviours to know before someone reports them as bugs

- ⚠ **Answering the confirm closes the drawer** — Cancel *and* OK. The drawer's click-outside
  handler sees the portalled modal as outside. The editor does not see `Running...`; reopening
  the drawer shows the result, because the content stays mounted. Save's confirm has always done
  this. Recorded in palimp as a quirk, not fixed.
- ⚠ **The drawer starts to scroll.** Its height is a fixed `40vh`; on a 776 px viewport the
  stock buttons fill the body exactly, and one action overflows it by 5 px idle, ~25 px with the
  result line, ~120 px with an error. Everything is reachable by scrolling, but the user row and
  logout are what scroll out first. **This is what your check "the drawer is fully usable with
  the action present" will meet** — see step 7.
- ⚠ **A dead token: Publish disables itself, the action does not.** Publish reads
  `Publish token expired` from its status poll; the action never polls, so it stays pressable
  and fails *after* the press, with the auth cause. Same token, same remedy.
- ⚠ **`statusText` is still empty over HTTP/2**, so a failure reads `GitHub dispatch failed: 404`
  with a trailing space. Unchanged from 1.9.0.
- ⚠ **The `production.yml` run does not appear in Publish's status icon** — correctly: the icon
  follows the Publish workflow only. (On palimp's side both targets were one workflow for the
  test, where it *did* appear. Here they differ, so it should not.)

### 3. Bump the four `file:` paths

### 4. Verify the directory, then install

```sh

pnpm install                                                           # here
grep -c "1\.10\.0" pnpm-lock.yaml                                      # and no 1.9.0 left
```

### 5. `pnpm verify` on the bump alone, before the feature

```sh
pnpm verify        # gates + lint + build + check-eager-chunks
pnpm build:pages
pnpm weight
```

Doing the bump first, with no `extraTargets` yet, separates "the upgrade" from "the feature" in
the measurement. **Expect a small eager move:** `publish-github/dist/react.js` goes from 344 B to
781 B gzipped (the `extraTargets` mapping), and `@palimp/core`'s root gains
`PalimpDrawerActionsContext` (one `createContext`, a 307 B gz module). Both modules were already
in the eager graph — the `[locale]` layout imports the provider statically — so this is growth,
not a new edge. Roughly **half a kilobyte**, the plan's "few hundred bytes".

If `check-eager-chunks` reports `@palimp/core/admin` (antd, react-query, lucide) in an eager
chunk, **stop and report it.** Nothing in 1.10.0 should do that: the drawer half is behind the
same `next/dynamic` boundary as before, and the root entry imports nothing from `Admin/`.

### 6. The host change — one prop, and two env vars

**Preview build** sets `NEXT_PUBLIC_GITHUB_PRODUCTION_WORKFLOW=production.yml` and
`NEXT_PUBLIC_PRODUCTION_SITE_URL`. **Live build** sets neither, so the live site never grows a
button that republishes itself.

On the `PalimpGithubPublishProvider` the layout already renders — still a Server Component, no
new client file:

```tsx
const productionWorkflow = process.env.NEXT_PUBLIC_GITHUB_PRODUCTION_WORKFLOW;
const productionUrl = process.env.NEXT_PUBLIC_PRODUCTION_SITE_URL;

<PalimpGithubPublishProvider
  /* owner, repo, workflow, followAllEvents — unchanged */
  extraTargets={
    productionWorkflow && productionUrl
      ? [
          {
            id: "production",
            label: "Publish live site",
            workflow: productionWorkflow,
            confirm: {
              title: "Publish the live site?",
              okText: "Publish live site",
              content: `The public site at ${productionUrl} rebuilds from the saved content. Visitors see the change in a few minutes. The preview is not affected.`,
            },
          },
        ]
      : []
  }
>
```

Notes on that snippet:

- **`{url}` in the plan is this host's interpolation, not palimp's.** palimp renders `content`
  verbatim; there is no templating.
- **`[]`, not `undefined`, on the live build.** Equivalent at runtime (an empty list renders
  nothing and leaves the context untouched), and it avoids an `exactOptionalPropertyTypes`
  complaint if this host has that flag on.
- **`ref` is inherited** from the provider's `ref`, then `"main"`; set it on the entry only if
  `production.yml` must dispatch on a different branch. **`inputs` are not inherited.**
  `followAllEvents` does not exist on an extra target — it never polls.
- **The PAT needs Actions write on `production.yml` too.** It is the same token on the same
  repo, so a fine-grained token scoped to the repo already covers it; a token scoped narrower
  than that is the 2026-09-28 incident's shape again.

Then re-run step 5's gates with the prop in place; the numbers should not move beyond step 5's.

### 7. Verify for real

**No build in either repo can see any of this.** On the palimp side all five of the plan's
checks passed on 2026-10-19 against `examples/supabase-next` with a real PAT and the drawer
driven over CDP — the record is
[`plans/drawer-actions.md`](../plans/drawer-actions.md) §Verification run. **One difference
matters:** there, both targets were the *same* workflow. Here they are `preview.yml` and
`production.yml`, which is the configuration the feature is for. So:

1. **The action dispatches `production.yml`.** Confirm → OK, reopen the drawer:
   `Run <id> started`, the link opens that run, and it is a `production.yml` run on GitHub's
   Actions tab. ⚠ This rebuilds the **live site** — do it when the saved content is meant to go
   live, or ask first.
2. **Cancel dispatches nothing.** The confirm shows this host's strings with **Cancel focused**;
   Cancel leaves no result line and no new run.
3. **A garbage token reads the auth cause.** Set `publish_token` to garbage on the profile row,
   reload: Publish reads `Publish token expired`; the action is still pressable and fails with
   `GitHub dispatch failed: 401` and *"The publish token on your account was refused…"*. Restore
   the token.
4. **A renamed workflow reads the generic cause.** Point
   `NEXT_PUBLIC_GITHUB_PRODUCTION_WORKFLOW` at a file that does not exist: `Publish live site
   failed` (enabled), `404`, and *"The site was not rebuilt. … pressing Publish live site again
   is the retry."*
5. **Publish is unaffected**, and its status icon does **not** pick up the `production.yml` run.
6. **The drawer is fully usable with the action present** — the check the whole feature exists
   for, and the one palimp could not run on this host's viewport. Expect it to scroll (see the
   ⚠ above): it passes if every control is reachable and nothing in the page paints over it. If
   the scrolling is judged unacceptable, report it rather than restyling palimp's drawer from
   here — the drawer's fixed `40vh` is palimp's to change.
7. **The live build has no button.** Build without the two env vars and confirm the drawer
   matches 1.9.0.
