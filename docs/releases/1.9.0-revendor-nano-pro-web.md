## What 1.9.0 actually changes

Six runtime files and five version bumps. Nothing else is code.

| file | change |
| --- | --- |
| `libs/core/src/PalimpPublishAdapter.ts` | **new value export** `PalimpPublishAuthError extends Error` |
| `libs/core/src/index.ts` | re-exports it from `@palimp/core` |
| `libs/core/src/Admin/Devtools/usePublishButton.ts` | returns `error` and `reset`, plus a derived `tokenExpired`; `onClick` calls `reset()` before `mutate()` |
| `libs/core/src/Admin/Devtools/DevtoolsContent.tsx` | `publishLabel` gains `Publish token expired` (disabled) and `Publish failed` (enabled — the same button is the retry); the status button stays open-able while a dispatch error is set |
| `libs/core/src/Admin/Devtools/PublishStatusModal.tsx` | takes the rejection as `dispatchError`, renders it above the run rows with a plain-language cause, and captions the surviving rows as the older build |
| `libs/publish-github/src/client.ts` | **new value export** `GithubAuthError extends PalimpPublishAuthError`, with `readonly status`, thrown by `dispatchWorkflow` and `fetchRuns` for `401`/`403` only |

**No adapter contract, context, store, schema or `exports` map moved. No peer range changed.
Nothing in this host's application code has to change** — there is no `followAllEvents`-style
decision this time. The whole upgrade is a version bump, a reinstall and the verification.

### What the editor sees that they did not before

1. **A dispatch that fails says so, persistently.** The button reads `Publish failed` (still
   enabled) and the status modal reads `Dispatch failed` + the cause. Both are still true an hour
   later, which is the property a transient toast would not have had.
2. **A dead token disables the button before anyone presses it.** `usePublishRun` already polls
   `getLatestRun` with the same token on mount, so a `401`/`403` from that poll proves the token is
   dead; the label becomes `Publish token expired`, disabled.
3. **The modal no longer implies the old run is the new one.** A secondary line says *"Last known
   run — not the publish you just tried to start. The site is still serving this build."*

### Two behaviours to know before someone reports them as bugs

- ⚠ **`statusText` is empty over HTTP/2**, so the modal renders `GitHub dispatch failed: 404 ` with
  a trailing space rather than `404 Not Found`. Cosmetic; observed live.
- ⚠ **A poll failure disables Publish for its retry window with no explanation.** react-query
  retries before `error` is set, and `isLoading` is still true throughout — ~7 s for a retried
  `401`, ~2 s for a `404`. An editor who opens the drawer and presses immediately meets a dead
  button. Harmless, deliberate for now; if it is ever worth fixing, `isLoading` is the wrong gate
  and `isPending && !isError` is the right one.
- ⚠ **The `instanceof` check is class identity, so two resolved copies of `@palimp/core` make
  `tokenExpired` silently false** and the label falls back to `Publish failed`. It degrades rather
  than throws. The lockstep version is what keeps this honest — install all four tarballs at 1.9.0
  or none.

## Steps

### 1. Clear the 1.8.1 tarballs out of `vendor/` first

The trap `revendoring-palimp.md` names: `--out` only deletes a tarball of the *same name*, so
otherwise `vendor/` holds both versions and `--verify-only` dies with `pack: versions have drifted`.

```sh
rm ~/repositories/nano-pro-web/vendor/palimp-*-1.8.1.tgz
```

### 2. Get the 1.9.0 tarballs into `vendor/`

**Route A — copy the packed set (recommended).** Already packed from a clean tree at `e2a41a1`,
with the assertions run:

```sh
cp ~/.t3/userdata/attachments/palimp-1.9.0-tarballs/palimp-{core,fe-next,be-supabase,publish-github}-1.9.0.tgz \
   ~/.t3/userdata/attachments/palimp-1.9.0-tarballs/palimp-manifest.json \
   ~/repositories/nano-pro-web/vendor/
```

Four of the five, Supabase being the backend here — the manifest still lists five, which is what was
*packed*, and that is not a mismatch. `SHA256SUMS.txt` sits beside them:

```sh
cd ~/.t3/userdata/attachments/palimp-1.9.0-tarballs && shasum -a 256 -c SHA256SUMS.txt
```

Reproduced here, because that staging folder is outside both repos and may be cleaned:

which is exactly why route A exists.

### 3. Bump the four `file:` paths

In `package.json`, `-1.8.1.tgz` → `-1.9.0.tgz` for each of the four `@palimp/*` specifiers
(lines 29–32 as of `3dd0155`).

### 4. Verify the directory, then install

```sh
pnpm pack:all --verify-only --out ~/repositories/nano-pro-web/vendor   # from a palimp checkout
pnpm install                                                           # here
grep -c "1\.9\.0" pnpm-lock.yaml                                       # and no 1.8.1 left
```

`--verify-only` proves the state of `vendor/`, not of whoever packed it: five (here four) tarballs
at one version, `workspace:*` rewritten to a real version, every `exports` target actually shipped.
Expect the lockfile to move the four `@palimp/*` entries — and, per `revendoring-palimp.md`, possibly
some already-present `react-aria`/`react-spectrum` transitive pins. Not a reason to stop.

### 5. `pnpm verify`, and expect the eager-chunk gate to pass

```sh
pnpm verify        # gates + lint + build + check-eager-chunks
pnpm build:pages
pnpm weight
```

**The one thing worth knowing before you read `check-eager-chunks`:** `publish-github/dist/client.js`
gained a **runtime** import of `@palimp/core` in 1.9.0 — at 1.8.1 that file had *no* runtime imports
at all, only erased type-only ones. That sounds like a new eager edge and is not: `react.js`, the
provider the `[locale]` layout imports statically, already imports both `@palimp/core` and
`./client` at runtime, so core's root entry was already in the eager graph. The genuinely new
eagerly-reachable code is one bare `Error` subclass in each of the two packages. Expect a few dozen
bytes, in the noise against Turbopack's module renumbering.

If the gate *does* move, stop and report it rather than adjusting it — nothing in this upgrade should
pull `@palimp/core/admin` into an eager chunk, and every `fe-next` import of it is still
`next/dynamic`.

### 6. Verify for real — this is the whole point

**No build in either repo can see any of this.** `check-types` and `build` pass on the palimp side
and prove only that the error class resolves across the package boundary and that the widened hook
return still satisfies its consumers.

The good news: **all five steps have already been run on the palimp side**, against
`examples/supabase-next` with real Supabase credentials, a real fine-grained PAT, and the drawer
driven over CDP — the record is
[`plans/editor-safety/01-publish-failure-is-silent.md`](../plans/editor-safety/01-publish-failure-is-silent.md)
§Verification run. So this host's pass is
confirmation in *its own* configuration, not first contact. What is specific to here, and worth the
credentialed session:

1. **Renamed workflow → `Publish failed`.** Point `NEXT_PUBLIC_GITHUB_WORKFLOW` at a file that does
   not exist, press Publish: label `Publish failed` with the button still enabled, modal reads
   `Dispatch failed` / `GitHub dispatch failed: 404` and the **generic** cause string, not the auth
   one. ⚠ **Do not use "revoke the token" as the test for this** — with a token dead for both
   endpoints the button is disabled before it can be pressed, so the original plan's step 1 is
   unreachable by construction. Renaming the workflow is the test.
2. **Dead token → `Publish token expired`, disabled, with no press.** Set `publish_token` to a
   garbage string on the profile row, reload, open the drawer, wait ~7 s, touch nothing.
3. **Valid token → a real run.** `Publish` → `Dispatching...` → `Publishing...` → `Publish`, with the
   modal tracking the run to `success` without a reload, and the run id matching GitHub's Actions tab.
4. **Saved edits survive every one of the above.** The dispatch half failing must never touch the
   write half. By inspection it cannot — `useSaveButton` is a separate mutation on a separate
   adapter — but this host is where it is observed.
5. **`production.yml` as well as `preview.yml`**, if the two differ in token scope here. A token with
   repo read but no Actions write is the exact shape of the 2026-09-28 incident: the poll succeeds, the
   dispatch `403`s, and `Publish failed` is what should appear — *not* `Publish token expired`.

Leave `followAllEvents` exactly as [ADR 070](agent-guidelines/decisions/070-which-run-the-drawer-calls-latest.md)
settled it. 1.9.0 does not touch it.

## Boundaries

- **Do not modify the palimp repo, any of its worktrees, or the vendored copy in `node_modules`.**
  The library change is committed and in review as PR #13. A patch to the installed copy or to a
  tarball is lost on the next repack and makes the manifest lie about what is installed. Found a
  library bug? Report it.
- **Do not change this host's palimp integration code.** 1.9.0 requires nothing, and a change that
  looks required means something went wrong in steps 1–4.
- Credentials: steps 6.1–6.5 need the real publish PAT, a dispatchable workflow and the Supabase
  profile row. Don't guess at them — ask.

## Report back

One message: the `--verify-only` output, the lockfile diff summary, the `check-eager-chunks` and
`weight` results with row K's numbers, and each of the five checks in step 6 marked **pass / fail /
not run**. Mark anything unrun as *not run* rather than omitting it — the entire reason 1.9.0 exists
is that a failure nobody surfaces looks exactly like success.
